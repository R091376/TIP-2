# Deploy TIP-2 on Render (split services + JWT)

Blueprint file: [`render.yaml`](../render.yaml) at repo root.

## Auth model

- **JWT access token**, HS256, lifetime **8 hours** (`JWT_EXPIRE_HOURS=8`).
- Login returns `{ accessToken, tokenType, expiresIn, user }`.
- Frontend stores token in **`localStorage`** and sends  
  `Authorization: Bearer <token>` on API calls.
- **No session cookies** — works on mobile with split `tip2-web` / `tip2-api`.
- No refresh token: after 8h the user logs in again.
- Logout is client-side (discard token); server does not revoke JWTs.
- **Public market desk:** unauthenticated `GET /api/watchlist`, `/api/market/*`, `/api/symbols/{id}/*`, `/api/pattern-alerts`, `/api/pattern-statistics`, and **`/ws/live`** are allowed. `GET /api/auth/me`, `/api/paper/*`, `/api/admin/*`, watchlist writes, instrument search, and research query still require JWT.

## Services

| Service | Type | Root | URL shape |
|---------|------|------|-----------|
| `tip2-api` | Web (Python) | `backend/` | `https://tip2-api.onrender.com` |
| `tip2-web` | Static (Vite) | `frontend/` | `https://tip2-web.onrender.com` |

## One-time Blueprint setup

1. Push `main` to GitHub.
2. [Render Dashboard](https://dashboard.render.com) → **New → Blueprint**, or **Sync** existing.
3. Set **sync: false** secrets:

| Variable | Service | Value |
|----------|---------|--------|
| `DATABASE_URL` | tip2-api | Neon URL (`postgresql+psycopg://…?sslmode=require`) |
| `UPSTOX_ACCESS_TOKEN` | tip2-api | Long-lived Upstox access token |
| `CORS_ALLOWED_ORIGINS` | tip2-api | `https://tip2-web.onrender.com` (exact, no trailing slash) |

`JWT_SECRET` is auto-generated by the Blueprint.

### Already set by `render.yaml`

| Variable | Value | Why |
|----------|--------|-----|
| `TIP_WATCHLIST_STORE` | `postgres` | Neon |
| `JWT_EXPIRE_HOURS` | `8` | Access token lifetime |
| `JWT_SECRET` | generated | Signs Bearer tokens |
| `CORS_ALLOWED_ORIGINS` | FE + localhost | Browser CORS for split deploy |
| `PYTHON_VERSION` | 3.12.8 | Runtime pin |

Woodie S/R flags (optional kill switches; live freeze + stamp default ON):
`TIP_PATTERN_SR_ENABLED`, `TIP_PATTERN_SR_STAMP_ENABLED`,
`TIP_PATTERN_SR_RESEARCH_ENABLED`.
`TIP_PATTERN_SR_BACKFILL_ON_STARTUP` defaults **OFF** (historical repair only —
`backend/scripts/backfill_woodie_sr.py`). Live today-rows still freeze via `ensure_today`.
`TIP_TIMEFRAME_1M_ENABLED` defaults **OFF** (no 1m seed / chart chip). Set `true` to restore.
Frontend: `VITE_FEATURE_PATTERN_SR_RESEARCH` (default ON), `VITE_FEATURE_TIMEFRAME_1M` (default OFF).

### Migrating from cookie auth

On **tip2-api** Environment:

1. Ensure `JWT_SECRET` is set (long random). Code also accepts legacy `SESSION_SECRET` if `JWT_SECRET` is empty.
2. Set `JWT_EXPIRE_HOURS=8`.
3. Remove unused cookie flags: `SESSION_COOKIE_SAMESITE`, `SESSION_COOKIE_HTTPS_ONLY`.
4. Keep `CORS_ALLOWED_ORIGINS=https://tip2-web.onrender.com,...`
5. Redeploy **tip2-api** and **tip2-web** (FE must include Bearer client code).

## Deploy order

1. Deploy / sync Blueprint.
2. `GET https://tip2-api.onrender.com/api/health` → UP.
3. Redeploy tip2-web so `VITE_API_BASE_URL` is baked in.
4. Open FE → login `admin` / `admin`.

## Local vs production

| | Local | Render split |
|--|--------|----------------|
| FE API | relative `/api` + Vite proxy | `VITE_API_BASE_URL` → API origin |
| Auth | Bearer JWT in `localStorage` | same |
| CORS | localhost | FE origin |
| Cookies | not used | not used |

## Smoke checklist

- [ ] Health UP
- [ ] Login returns `accessToken` + `user`
- [ ] `/api/auth/me` with Bearer → 200
- [ ] `/api/auth/me` without Bearer → 401
- [ ] Incognito `/` shows charts (no login wall); `GET /api/watchlist` without Bearer → 200
- [ ] `/paper` while logged out → `/login?next=`
- [ ] Mobile login works (no cookie dependency)
- [ ] Watchlist + candles + live WS as a guest

## If login fails on mobile

1. Confirm FE build is the JWT client (not old cookie-only build).
2. Confirm API has `PyJWT` installed (redeploy after `requirements.txt` change).
3. CORS origin must match FE host exactly.
4. Clear site data and log in again (old cookie session is irrelevant).
